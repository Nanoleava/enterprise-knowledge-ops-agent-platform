-   Spring Boot REST API

-   Document业务基础
-   DocumentChunk业务基础

-   Spring Security
-   Principal资源隔离

# 五、数据库设计改造规则

## 目标

让Document从：

    用户输入文本记录

升级为：

    上传文件生命周期对象

------------------------------------------------------------------------

## document新增信息方向

需要支持：

### 文件元数据

包括：

-   原始文件名
-   服务端存储文件名
-   文件类型
-   文件大小
-   文件路径信息
-   文件校验信息（如项目设计需要）

规则：

1.  原文件名只用于展示。
2.  原文件名不能参与磁盘路径拼接。
3.  实际存储名称必须由服务端生成。

------------------------------------------------------------------------

## 文档处理状态

必须增加明确状态。

至少区分：

    PENDING
    等待处理

    PROCESSING
    正在处理

    SUCCESS
    处理成功

    FAILED
    处理失败

要求：

不能使用一个模糊字段同时表示：

-   上传状态
-   解析状态
-   切片状态

DAY1重点关注：

parse_status

chunk_status保持后续扩展。

------------------------------------------------------------------------

# 六、文件上传功能设计规则

## 上传接口职责

上传接口负责：

-   接收Multipart文件
-   获取当前用户身份
-   校验知识库归属
-   调用文件存储服务
-   创建Document记录

上传接口禁止：

-   直接解析文件
-   直接操作磁盘路径
-   编写复杂业务逻辑

------------------------------------------------------------------------

# 七、文件安全规则

## 1. 文件名安全

用户上传：

    test.md
    ../../application.yml

都不能直接作为服务器文件名。

必须：

-   使用UUID或随机名称
-   服务端生成存储路径

------------------------------------------------------------------------

## 2. 路径安全

必须保证：

最终文件路径：

    storageRoot + relativePath

经过规范化后：

始终位于：

    storageRoot

内部。

禁止：

-   ../路径穿越
-   绝对路径写入
-   用户控制存储目录

------------------------------------------------------------------------

## 3. 文件类型安全

不能只相信：

-   Content-Type
-   文件扩展名

必须进行基础校验。

DAY1支持：

-   TXT
-   Markdown

其他格式进入后续阶段。

------------------------------------------------------------------------

# 八、文件存储模块设计规则

新增文件存储职责：

## FileStorageService

负责：

-   创建目录
-   生成安全文件名
-   保存文件
-   删除文件
-   文件路径校验

禁止：

Controller直接调用文件IO。

------------------------------------------------------------------------

# 九、文档解析设计规则

## Parser设计

解析逻辑必须独立。

推荐：

    DocumentParser接口

            ↓

    TxtParser

    MarkdownParser

    PdfParser(后续)

------------------------------------------------------------------------

Parser职责：

负责：

    文件
     ↓
    文本内容

不负责：

-   数据库保存
-   HTTP响应
-   用户权限

------------------------------------------------------------------------

DAY1只实现基础清洗。

包括：

-   BOM处理
-   换行统一
-   无意义空白处理
-   空文本检查

禁止：

-   破坏Markdown结构
-   删除标题信息
-   过度格式化

    ↓

每一层职责明确。

------------------------------------------------------------------------

# 十二、失败处理规则

必须考虑失败场景。

## 文件保存失败

要求：

-   不创建错误Document记录。

------------------------------------------------------------------------

## 数据库保存失败

要求：

-   删除已经保存的文件。
-   避免产生孤儿文件。

------------------------------------------------------------------------

## 解析失败

要求：

数据库：

    parse_status=FAILED

同时：

-   保留原文件用于重试。
-   不生成错误文本数据。

------------------------------------------------------------------------

# 十三、DAY1 API设计要求

## 1. 上传接口

用途：

上传文件并创建Document。

规则：

必须：

-   JWT认证
-   owner校验
-   文件校验
-   返回documentId

------------------------------------------------------------------------

## 2. 文档解析接口

用途：

触发解析。

规则：

必须：

-   校验owner
-   防止重复处理
-   更新解析状态

------------------------------------------------------------------------

## 3. 状态查询接口

用途：

查看处理状态。

返回：

包括：

-   documentId
-   parseStatus
-   chunkStatus
-   错误摘要

禁止返回：

-   服务器绝对路径
-   文件正文
-   敏感异常堆栈

------------------------------------------------------------------------

# 十四、DAY1验证方案

验证目标：

不是验证接口200。

而是验证完整工程闭环。

------------------------------------------------------------------------

# 1. 正常上传验证

准备：

TXT文件。

验证：

数据库：

-   Document新增
-   文件元数据正确

文件系统：

-   文件存在
-   路径正确

------------------------------------------------------------------------

# 2. Markdown上传验证

验证：

-   文件保存成功
-   Markdown内容解析成功
-   document.content正确

------------------------------------------------------------------------

# 3. 越权验证

场景：

用户B访问用户A知识库。

期待：

-   HTTP 403
-   数据库无新增
-   文件系统无新增

------------------------------------------------------------------------

# 4. 空文件验证

上传0KB文件。

期待：

-   返回业务错误
-   不产生垃圾文件
-   不产生Document记录

------------------------------------------------------------------------

# 5. 非法类型验证

上传：

    exe文件
    伪装txt文件

期待：

拒绝处理。

------------------------------------------------------------------------

# 6. 解析失败验证

上传损坏文本文件。

期待：

    parse_status=FAILED

并且：

-   不生成错误content
-   可重新处理

------------------------------------------------------------------------
